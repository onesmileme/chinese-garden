# Guwendao 唐诗审核与批量激活设计

## 目标

为已导入内容后台的 320 首古文岛唐诗候选建立可审计、可复现的审核清单，并通过现有管理 API：

- 激活 310 首通过审核且不与正式诗库重复的候选；
- 归档 10 首与现有 `ACTIVE` 唐诗正文重复的候选；
- 保留逐条权限校验、乐观锁和操作审计；
- 支持执行中断后的安全续跑；
- 阻止重复唐诗通过其他入口被误激活。

本次完成后，唐诗总数应为 `ACTIVE = 333`，其中 23 首为原正式内容，310 首为本次激活的古文岛候选。

## 当前状态

后台当前包含：

| 范围 | 状态 | 数量 |
| --- | --- | ---: |
| 原正式唐诗 | `ACTIVE` | 23 |
| `sc-gwd-*` 古文岛候选 | `DRAFT` | 320 |

对作者和正文规范化后比较，320 首候选中有 10 首与原正式唐诗重复：

- 早发白帝城
- 寻隐者不遇
- 江雪
- 静夜思
- 登鹳雀楼
- 春晓
- 鹿柴
- 登乐游原
- 相思
- 回乡偶书

剩余 310 首在候选集内的“作者+标题”和“作者+正文”均唯一。候选的空 `charRefs` 符合当前内容模型，不阻塞激活。

## 方案选择

采用清单驱动的 CLI 编排，复用现有单条管理 API。

未选择新增后端批量接口，因为现有接口已经提供所需的角色校验、revision 乐观锁、校验和审计语义；新增批量事务会扩大协议与故障边界。未选择一次性 shell 或 SQL 脚本，因为它们无法提供稳定的清单契约、自动化测试和可靠续跑能力。

本方案不新增数据库表，不直接修改内容表，也不改变导入批次记录。

## 审核标准

本次审核是可自动验证的技术与内容一致性审核，检查：

1. 候选来自固定的 320 条 `guwendao-tang-poem-v2` 制品。
2. ID、来源 ID、来源 URL、来源哈希和 revision 未漂移。
3. 标题、作者和诗句完整，诗句数组非空。
4. 候选集内“作者+标题”和“作者+正文”唯一。
5. 与当前 `ACTIVE` 唐诗比较后，不存在相同的规范化作者和正文。
6. 现有 `ContentValidator` 返回零阻断问题。

适龄性分级、注释、翻译、音频、图片和逐字知识点关联不在本次审核范围。310 首候选继续使用保守的 Level 5、Difficulty 5 和 `promotionRequired = true`。

## 唐诗身份规范

TS 清单生成器与 Java 后端校验器使用相同的唐诗正文身份规则：

- 作者执行 Unicode NFKC 规范化，去除 Unicode 空白和标点；
- 正文按 `lines` 原顺序连接；
- 正文执行 Unicode NFKC 规范化，去除 Unicode 空白和标点；
- 身份键为 `规范化作者 + NUL + 规范化正文`。

两端通过同一组黄金向量验证规范化结果。身份键只用于重复判断，不修改展示标题、作者或诗句。

后端仅把与 `ACTIVE` 唐诗身份相同的对象视为激活阻断项。`DRAFT` 或 `ARCHIVED` 内容不阻断激活；候选自身由调用方从比较目录中排除。

## 审核清单

新增机器可读、受版本控制的 NDJSON 清单：

`frontend/content/reviews/poems-guwendao-tang-320-review.ndjson`

清单覆盖全部 320 条候选，按内容 ID 升序排列：

- 310 条使用 `decision = ACTIVATE`；
- 10 条使用 `decision = ARCHIVE_DUPLICATE`。

每行至少包含：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定内容 ID |
| `expectedRevision` | 执行时要求的 revision |
| `expectedStatus` | 生成清单时的状态，必须为 `DRAFT` |
| `title`、`author` | 人工可读标识 |
| `sourceId`、`sourceHash` | 来源追踪信息 |
| `payloadHash` | 当前后台 payload 的规范 SHA-256 |
| `poemIdentityHash` | 规范化作者和正文身份的 SHA-256 |
| `decision` | `ACTIVATE` 或 `ARCHIVE_DUPLICATE` |
| `checks` | 已通过的固定审核规则 |
| `duplicateOf` | 重复项对应的 `ACTIVE` 内容 ID；激活项为 `null` |

同时新增简短摘要：

`frontend/content/reviews/poems-guwendao-tang-320-review-summary.md`

摘要记录输入制品 SHA-256、清单 SHA-256、规则版本、决策计数、10 组重复映射及执行前状态。摘要不复制 310 行正文。

生成失败时不得替换已有清单。以下任一情况均为失败：

- 候选不是精确的 320 条或来源制品哈希不匹配；
- 后台项目缺失、type/status/revision/payload 与候选不一致；
- 决策数量不是精确的 310/10；
- 候选内部存在正文身份冲突；
- 某个重复项没有唯一的 `ACTIVE` 对应项；
- 任一待激活项与 `ACTIVE` 唐诗重复。

## 后端重复保护

`ContentValidator` 增加唐诗正文重复问题码。验证 `POEM` 时，若候选和任一 `ACTIVE` 唐诗具有相同身份键，则返回阻断问题，路径指向 `/payload/lines`，消息包含重复目标 ID。

该规则同时保护：

- 管理后台单条激活；
- 清单驱动批量激活；
- 后续使用相同应用服务的其他入口。

本次不增加数据库唯一索引。唐诗身份来自 JSON payload，使用索引会引入冗余投影和迁移复杂度，不符合本次范围。

## 执行流程

新增 `apply-poem-review` CLI 命令。命令接收审核清单、管理 API 地址、管理 token 和报告输出路径。
管理 token 对应的主体必须同时具备 `REVIEWER` 和 `EDITOR`：校验及激活需要
`REVIEWER`，归档需要 `EDITOR`。actor 由后端认证结果确定，CLI 不允许通过请求头覆盖。

### 全量预检

任何写操作前，命令必须：

1. 校验清单结构、排序、哈希和 `310/10` 决策数量。
2. 获取全部 320 条后台内容。
3. 对每条内容核对 type、revision、payload 哈希和允许的当前状态。
4. 对 310 条待激活内容调用现有 `validate` API，要求全部通过。
5. 对 10 条重复内容确认 `duplicateOf` 仍为 `ACTIVE` 且身份哈希匹配。

预检失败时不发送任何 `activate` 或 `archive` 请求。

### 状态迁移

预检通过后按稳定 ID 顺序执行：

1. 先归档 10 条 `ARCHIVE_DUPLICATE` 内容。
2. 再激活 310 条 `ACTIVATE` 内容。
3. 每次调用携带清单中的 `expectedRevision`。
4. 后端继续在单条事务中执行状态修改与审计写入。

顺序执行，不并发写入，以保持故障位置、审计顺序和服务负载可预测。

## 幂等与中断恢复

数据库状态是恢复依据，不维护额外 checkpoint：

- 当前为 `DRAFT` 且 revision、payload 哈希匹配时，执行清单决策；
- 当前已是目标状态，且 revision、payload 哈希仍匹配时，记录 `SKIPPED_ALREADY_APPLIED`；
- 当前为其他状态，或 revision/payload 漂移时，预检失败；
- 激活和归档不会增加 revision，因此成功项可被可靠识别。

执行进程被终止或网络中断后，重新运行同一命令会跳过已完成项并继续剩余操作。已经提交的单条事务不回滚。

## 错误处理与报告

以下情况立即停止执行：

- HTTP 认证或权限失败；
- `409 CONTENT_REVISION_CONFLICT`；
- `422` 内容校验失败；
- 内容、重复目标或哈希漂移；
- 非预期状态；
- 网络错误或无法解析的响应。

错误信息必须包含阶段、内容 ID、HTTP 状态和后端错误体，但不得输出管理 token。

执行报告原子写入指定 JSON 文件，包含：

- 清单哈希；
- 开始和结束时间；
- `activated`、`archived`、`skipped`、`failed` 计数；
- 每条内容的最终结果；
- 首个失败项及错误摘要。

运行报告用于操作复盘；数据库审计表仍是状态变更的权威审计来源。

## 测试策略

实现严格使用 TDD。

### Java

覆盖：

- 与 `ACTIVE` 唐诗作者和正文相同会产生重复阻断问题；
- 不同作者、不同正文不误报；
- `DRAFT` 和 `ARCHIVED` 重复项不阻断；
- Unicode 空白、标点和兼容字符按黄金向量规范化；
- `activate` 在重复问题存在时不改变状态、不写成功审计。

### TypeScript

覆盖：

- 清单确定性生成及精确的 320、310、10 计数；
- 来源、revision、payload 和重复映射漂移检测；
- 候选内部冲突和重复目标不唯一时拒绝生成；
- 全量预检失败时零写请求；
- 成功执行顺序及审计 API 参数；
- 已完成项跳过和中断续跑；
- revision 冲突、校验失败、权限失败和网络失败；
- 执行报告原子写入；
- CLI 参数、退出码和敏感信息不泄漏。

仓库级制品测试固定候选输入哈希、清单哈希、决策计数和 10 组重复映射。前端逻辑保持 100% Vitest 覆盖率，并执行 TypeScript typecheck；后端执行模块测试和集成测试。

| 验收项 | 期望 |

| 全部 `POEM / ACTIVE` | 333 |
| `sc-gwd-* / ACTIVE` | 310 |

## 非目标

- 不删除候选或导入审计记录；
- 不修改 23 首原正式唐诗；
- 不发布新的内容 release；
- 不修改诗词等级、难度、标签或正文；
- 不补充 `charRefs`、拼音、翻译、注释、音频或图片；
- 不建设通用后台批量编辑界面；
- 不处理 1,000 条成语候选。
